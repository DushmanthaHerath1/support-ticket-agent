# Support ticket agent — build plan (v1)

A support agent that looks up orders, answers questions, and can issue refunds — but only after a human approves. Built to demonstrate: LangGraph ReAct loop, memory, middleware (summarization + human-in-the-loop), structured output, and streaming.

---

## 1. Frontend screens

Keep this to two screens. Don't over-build the UI — the agent logic is the point.

### Screen A — Chat
- Message list (user / assistant bubbles), assistant messages **stream** token-by-token.
- Input box + send button.
- A small "thinking" indicator when a tool is being called (e.g. "Looking up order #1234...").
- If the agent's current turn is blocked on a pending approval, show a banner: "Waiting for approval to issue a $42.00 refund" with a link to Screen B.

### Screen B — Pending approvals
- List of pending `issue_refund` calls: customer, order id, amount, reason (as generated by the agent).
- Three actions per item: **Approve**, **Reject**, **Edit** (edit lets you change the refund amount before approving).
- Once actioned, the corresponding chat conversation resumes automatically — poll or use a websocket to reflect this without a manual refresh.

Optional Screen C (nice-to-have, not required for v1): a "resolved tickets" table showing the structured output logged per conversation — category, sentiment, resolution, refund amount. This is the screenshot you'd actually use for the LinkedIn post.

---

## 2. Backend endpoints (FastAPI)

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/chat` | Send a user message for a given `conversation_id`. Streams the assistant's response (SSE or chunked response). If the graph hits the HITL interrupt, the stream ends with an `awaiting_approval` event instead of a normal completion. |
| `GET` | `/conversations/{id}` | Fetch full message history for a conversation (used on page load/refresh). |
| `GET` | `/approvals/pending` | List all pending `issue_refund` interrupts across conversations, for Screen B. |
| `POST` | `/approvals/{id}/approve` | Resume the graph with the approved (possibly edited) tool call. |
| `POST` | `/approvals/{id}/reject` | Resume the graph with a rejection, letting the agent respond accordingly. |
| `GET` | `/tickets` | List resolved tickets with their structured output (category, sentiment, resolution, refund_amount). Optional Screen C. |

Notes:
- `conversation_id` is how you scope memory — pass it through to LangGraph's checkpointer (`thread_id`).
- The HITL interrupt is native to LangGraph (`interrupt()` inside the tool node, or wrap the tool with the middleware pattern from your notebook) — you don't need to hand-roll a queue. The checkpointer persists the paused state; `/approvals/{id}/approve` just resumes the graph from that checkpoint with the human's decision injected.

## 3. Database

Four tables is enough. Use Postgres (or SQLite for the demo — Postgres if you want the LinkedIn post to say "production-ready").

**customers**
- `id`, `name`, `email`

**orders**
- `id`, `customer_id` (FK), `item`, `amount`, `status`, `created_at`

**conversations**
- `id`, `customer_id` (FK), `created_at`
- LangGraph's own checkpointer table(s) handle the actual message/state persistence (use `langgraph-checkpoint-postgres` — don't reinvent this) — this table is just your app-level index into `conversation_id`s per customer.

**tickets** *(this is your structured-output sink — the schema mirrors the Pydantic model your agent returns at resolution)*
- `id`, `conversation_id` (FK), `category`, `sentiment`, `resolution`, `refund_amount` (nullable), `resolved_at`

**refund_approvals**
- `id`, `conversation_id` (FK), `order_id` (FK), `proposed_amount`, `reason`, `status` (pending/approved/rejected/edited), `final_amount`, `decided_at`

## 4. LangGraph agent design

**State** (extends `MessagesState`):
```python
class SupportState(MessagesState):
    customer_id: str
    order_context: dict | None  # cached order lookup, avoids re-fetching
```

**LLM Strategy (Dual-Model Architecture):**
- **ReAct Tool-Calling Core:** Groq `qwen/qwen3.6-27b` — ultra-fast function calling loop and order status/eligibility/refund policy evaluation.
- **Conversational & Structured Output Engine:** Google `gemini-2.5-flash` — conversation summarization, clean customer-facing streaming responses without reasoning tokens, and strict `TicketResolution` structured extraction.

**Nodes:**
- `tool_calling_llm` — Groq `qwen/qwen3.6-27b` bound to `[lookup_order, check_refund_eligibility, issue_refund, resolve_ticket]`
- `tools` — `ToolNode` executing queries. `issue_refund` is wrapped in HITL middleware so calling it triggers `interrupt()` and the graph checkpoints there.
- `summarize` — Google `gemini-2.5-flash` runs before `tool_calling_llm` if message history exceeds token threshold.
- `structured_output` — Google `gemini-2.5-flash` final node that runs when `resolve_ticket` is triggered, generating strict `TicketResolution` Pydantic models for the `tickets` table and emitting clean customer concluding text.

**Edges:**
```
START → summarize → tool_calling_llm
tool_calling_llm → (tools_condition) → tools | structured_output | END
tools → tool_calling_llm   # ReAct loop
```

**Tools to write:**
```python
@tool
def lookup_order(order_id: str) -> dict: ...

@tool
def check_refund_eligibility(order_id: str) -> dict: ...

@tool
def issue_refund(order_id: str, amount: float, reason: str) -> dict:
    """Issues a refund. Requires human approval before executing."""
    ...
```

## 5. Build order (few hours)

1. **Agent first, no UI.** Get the LangGraph agent working end-to-end in a notebook exactly like the ones you already have — tools, ReAct loop, HITL interrupt, structured output, checkpointer with `thread_id`. This is the part worth your time.
2. **Wrap it in FastAPI.** One `/chat` endpoint that invokes the graph with `thread_id=conversation_id` and streams `.stream()` output. Add the two approval endpoints.
3. **Seed the database** with a handful of fake customers/orders so demos look real.
4. **Generate the frontend with AI** (two screens, per above) — point it at your endpoints, verify streaming and the approval flow work end to end.
5. **Run three demo conversations**, screenshot the approval moment and the resolved-tickets view — this is your LinkedIn content.
